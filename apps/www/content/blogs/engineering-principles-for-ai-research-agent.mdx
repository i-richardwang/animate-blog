[Dossier](/projects/dossier) 是我最近做的一个项目，让 Claude Code agent 在一张知识图谱上做组织情报研究，跨会话持续累积和维护。它的具体设计记录写在[构建组织情报研究系统](/docs/ai/applications/building-knowledge-graph-for-org-research)里。这篇文章讲在做这个项目过程中浮现出的几条判断，关于"怎样给一个做长期研究的 agent 构建工作环境"，会用 Dossier 的具体做法来说明。

我们最初的想法只是让一个 Claude session 帮忙整理材料，很快就发现：让 Agent 真正完成这种长期研究工作所需要的工程投入，远超过"写一个好 prompt"的范畴。实际撞到的问题几乎都是研究类任务的固有特征：材料体量远超单次上下文容纳能力，结论需要跨越多个会话沉淀，事实需要随后续证据被强化或推翻，错误一旦写入就会被后续推理当作前提复用。这些约束在单 Agent 框架内解决不了，它们要求把"如何工作"这件事本身做成一个有状态、有约束的环境。

这篇文章整理在这个过程中浮现出的几条原则。完稿前不久，OpenAI 公开了一份名为 Harness Engineering 的工程实践，描述他们用 Codex agent 群体写代码时沉淀的设计原则。里面不少判断和我们这边对得上。

## 规则靠工具执行比文档提醒更可靠

Agent 能改变系统状态的唯一入口是工具层，它的设计决定了整套系统的下限：选择什么样的形态，暴露什么样的接口，做多严格的校验。

Agent 拿到写权限大致有三种方式：

|  | 裸 SDK | MCP | 领域 CLI |
|---|---|---|---|
| **语义层拦截** | 无，语法正确即可写入 | 有，工具定义可带校验 | 有，参数校验编码领域规则 |
| **上下文开销** | 低 | 高（启动时全量加载） | 低（按需加载） |
| **领域规则** | 靠 prompt 提醒 | 可选实现 | 强制执行，报错即修复路径 |
| **错误暴露时机** | 下游分析时才发现 | 调用时 | 调用时 |

Dossier 选的是领域 CLI：所有数据写入收敛到一个 TypeScript CLI（`scripts/db.ts`），二十余条命令覆盖实体注册、关系写入、任职记录、观察和来源管理。

选型之外，更要紧的是这层接口做多严格的校验。在 Dossier 里，写入一条带证据的记录必须显式传入 `--confidence`，漏传直接报错，报错信息附带什么场景该用什么分值；写入关系或任职记录必须在 `--is-current` 和 `--not-current` 之间二选一，逼 agent 每次表态这条信息是关于当前还是历史；注册新实体时 CLI 自动做向量检索，发现近似名字就提示而不是静默创建。这些规则写在 prompt 里 agent 容易忽略，写在工具校验里就是硬墙，撞上去立刻得到反馈，而且反馈本身就是修复路径。

**约束的可靠性来自"无法绕过"，而不是"提醒得足够多次"。** 一条规则一旦被强制在工具层，就不再需要在每个 skill 文档里重复。agent 即便忘了，第一次调用就会被纠正。

## 指令文档分层组织并按需提供

随着 agent 在一个 repo 内承担的工作越来越多，关于"如何在这个项目中工作"的指令也会快速膨胀。一个常见但不奏效的做法是把所有规则都堆在一份入口文件里，希望 agent 一次性读完然后照做。

问题是文档一旦变长，就会开始挤占 agent 的有效上下文，挤掉任务本身、相关代码、必要的领域知识。另外，长文档很快开始腐烂：规则之间互相矛盾、过期内容无人维护、agent 无法判断哪条还成立。

有效的做法是分层。入口文档被刻意压短，主要承担目录的功能：告诉 agent 每一类工作去哪里找规则。各个工作流有独立的规则文档，只在需要时加载。工作对象的上下文（背景信息、目标、优先级）也独立成文件，和方法论解耦。Dossier 的文档就是这个结构：CLAUDE.md 只做目录，四个 skill（/ingest、/research、/reconcile、/analyze）各有独立的规则文件，每个研究项目有自己的 context 文件定义背景、实体清单和待解问题。新增一个研究主题只需要加一份 context，skill 本身完全不用动。

![Dossier 文档分层结构：CLAUDE.md 入口指向 skill 规则文件，skill 按项目名加载研究上下文](/ai/applications/dossier-doc-hierarchy.png)

Agent 启动时只看到入口和当前任务相关的少量内容，需要某个工作流时才把对应文档拉进上下文。这种结构让维护可以局部进行：修改一个工作流不需要触碰入口文档，新增一类工作对象不需要改动任何方法论。**入口文档的职责是引路，不是把所有知识一次灌完。**

## 定义完成标准比规定操作步骤更有效

Skill 文件的写法同样容易出错。常见的做法是把它写成操作手册，详细规定 agent 每一步该做什么、按什么顺序、用哪个工具。这种写法在简单任务里勉强能用，到了开放式研究场景下会立刻暴露问题：路径依赖太死，无法处理预料外的情况，随着模型能力升级反而成了天花板。

**描述目标和标准，不规定路径**。与其写"先调某某搜索命令，再调某某写入命令，然后判断……"，不如定义"这件事做对了应当满足什么标准"：信息覆盖了哪些必要维度，证据来源是否充分，置信度赋值是否合理。怎么达到这些标准是 agent 自己的判断空间。Dossier 里最能说明这一点的是 /reconcile：它定义了六条图谱健康标准（实体唯一性、事实去重、时间一致性、结构化优先、矛盾显式化、置信度对齐），以及按风险分层的修复框架，但不规定以什么顺序检查、每次走多深。/research 也是同样的思路：定义人物和组织各自需要覆盖的维度，但搜什么、怎么搜交给 agent 判断。

这种写法的前提是相信 agent 有判断力。它是研究员，不是流程执行器。人的工作是划清边界和定义标准，让 agent 自己选路。

这条原则和工具层的约束搭配使用：**工具画边界，skill 定标准**。合在一起就是 agent 的工作空间，边界清晰，路径自由。

## 让研究成果跨会话持续积累

研究的本质是长跑。一项有意义的调查，公开材料的体量从一开始就远超任何单次上下文窗口能容纳的范围；新的证据随时间陆续出现；早期的判断会被后续材料修正甚至推翻。所以这种工作不可能在一个 session 内完成，也不应当被绑定在任何一次 session 的内存里。

所有研究产出需要一个持久化的结构化存储来沉淀。Dossier 用 PostgreSQL 构建了这个存储，图谱分三层：实体层记录人物和组织，事实层记录它们之间的关系和观察，来源层把每条事实绑定到具体材料的具体段落。

![Dossier 知识图谱数据模型：实体层、事实层、来源层的关系](/ai/applications/dossier-knowledge-graph-schema.png)

每一次 session 启动时，agent 不从零开始，而是从已有的状态读取：它可以查询某个实体当前的已知信息，可以看到上一轮标记为待验证的记录，可以找到尚未被研究的空白。

这份状态承担三个职能：

- **跨会话的连续性**：一项横跨数周、数十个 session 的研究，新进入的 session 不需要被"补背景"。它读取存储就能知道目前已经查清楚了什么、哪里还有空白。
- **证据的可追溯**：每条记录都带来源引用，可以一路回溯到具体材料里的具体段落。这让后续修正成为可能：当一份新证据与现有结论冲突时，agent 可以判断旧结论的证据强度，决定是覆盖、并存还是标记为有争议。
- **协作的天然支持**：因为状态本身就有约束（唯一索引、写入前的检索去重），多个 session 即便并行运行也不会互相冲突。这是带约束的持久状态顺带获得的能力。

Agent 的工作产出如果是知识而非代码，工程上最关键的投入就是让推理之间能够稳定地累积。**持久状态就是这种累积的载体。**

## 不确定的信息同样值得正式记录

研究类工作和软件工作有一个关键差异：在软件里，大多数事情有明确对错；在研究里，"不知道"和"不确定"是常态。第一手得到的通常只是有线索的猜测，需要后续证据来强化或推翻。

如果状态层只能存"已经确定的事实"，agent 就只有两个糟糕的选择：要么把猜测当事实写入，要么把发现丢弃。前者会快速污染数据，后者会损失信息。两种都会让长期研究失去累积的意义。

所以我们把不确定性直接嵌进了 Dossier 的数据模型：

- **置信度字段**：每条记录必须带一个 0-1 的 confidence 分值，由证据强度决定。官方公告给 0.9，访谈报道给 0.7，推断给 0.5 或更低。这个字段在 CLI 层强制校验，漏传直接报错。
- **状态生命周期**：每条事实有明确的状态流转（`draft → confirmed → disputed → deprecated`）。一条记录可以从初步判断演进到被多个独立来源确认，也可以被新证据降级为有争议。
- **原始信号和结构化结论分开存储**：能压成关系的（A 向 B 汇报、C 领导 D）写入关系表，压不动的（"此人在内部被视为铁腕管理者""该团队士气低落"）写入观察表。"先存着、后续再看能不能结构化"这种中间态是合法的。

![事实状态生命周期：draft 经多来源交叉验证进入 confirmed，遇到矛盾证据进入 disputed，最终可能被废弃为 deprecated](/ai/applications/dossier-fact-status-lifecycle.png)

这些都是数据建模层面的工作，但在长期研究里缺一不可。**任何一项严肃的研究都会在很长一段时间内停留在"我知道一些事，但还不能下定论"的状态。** 强迫 agent 把每条记录都标成"事实"或"不写"，等于是在剥夺研究本应具有的渐进性。

这个问题不限于研究系统。任何跨会话维护记忆的 agent 都会面对类似的状况：记忆会过时，会互相矛盾，可靠性会随时间衰减。在 agent memory 的设计中，怎样表达信息的可靠性和时效性是一个值得考虑的问题。

## 数据治理是研究流程的固定环节

即便每一条单独的写入都合规，状态整体仍然会随着时间逐步偏移：重复的实体、过时的记录、互相矛盾的陈述。研究越长、写入越多，偏移越明显。agent 又倾向于复刻状态里已有的模式，包括那些不太好的模式，所以这种偏移是结构性的。

最朴素的应对方式是人工周期性清理。但数据量上去后这种做法立刻不可持续，而且人会疲惫、标准会松动。

可持续的方式是把治理做成系统的一个显式阶段。Dossier 的 /reconcile 就承担这个角色：按前面提到的六条健康标准逐项检查，修复动作按风险分三层处理（低风险直接修，中风险修完报告，不可逆操作标记等人判断）。检查过程中发现某个核心实体信息严重不足时，它还会启动一个独立的 /research 去补全，补完后回来验证新写入的质量，每轮最多派一次，避免递归失控。

**治理不能是周期性事件，必须是流程的一部分。** 在数据量低的系统里，偶尔清理一次也许够用；在持续增长的研究档案里，一周积累的偏差量足以让后续工作建立在错误的基础上。把治理编码成系统的显式阶段，是让研究在长期运行中保持可信的唯一方式。

## 结语

这几条原则讨论的事情各不相同，但底层指向同一个判断：

**为做长期研究的 Agent 构建工作环境，本质上是把人对研究质量的判断前置到工具、约束和数据模型里，而不是后置到审查环节。**

人的角色从执行者变成了立法者：决定边界在哪里、把判断怎么编码进系统、什么时候需要重新校准。Agent 在这套环境里有完整的判断空间，但所有判断的"形态"（记录格式、证据结构、不确定性表达、生命周期）都是被环境塑造好的。它能跑得多远，取决于环境帮它管住了多少容易出错的地方。

这些原则来自研究类 agent 的实践，但指向的问题更普遍。**只要 agent 承担的工作需要高保真、长期运行、产物需要被持续信任，工程师很可能会走向相似的做法：设计接口、收敛约束、组织上下文、维护长期一致性。**
