在讨论如何让 Agent 落地业务时，行业里的焦点往往集中在底层模型能力或 Prompt 调优上。但在真实的生产环境中，我发现这其实并非最大的瓶颈。

过去一年，在真实的业务场景里反复踩坑后，我陆续沉淀出了 [DataPilot](/projects/datapilot)（批量处理平台）、[Better Skills](/projects/better-skills)（质量评测工具）和 [Talent Graph](/projects/talent-graph)（人才标签系统）这几块基础设施。在这个过程中我最大的感触是：搓一个好看的单次对话 Demo 很容易；但要让系统稳定地跑完上万条非标数据、科学度量质量的升降、用确定的机制去约束不确定的 AI 输出，才是真正的挑战。

让 Agent 可靠地工作，本质上已经不是单纯的“AI 调优”问题了。我们需要为模型搭建一套坚固的“脚手架”——即业界所说的 Harness Engineering（外围与约束工程）。为了把大模型从玩具级别的“对话框”拉进真实的“生产线”，我们主要在以下几个维度做了一系列工程化基建。

## 从单次对话到生产级批量处理

我们的业务场景里，最先凸显的就是批量处理的需求。上万条公司名需要标准化，"字节""ByteDance""字节跳动(上海)有限公司"是同一家公司，在数据库里可能有几十种写法。几千份简历需要做结构化提取，不是读一份出一份结果，是按统一的字段定义逐条处理。这些场景都需要按统一标准把大量数据跑完。

现有的 Agent 产品大多是围绕单次对话设计的，这种一问一答的模式其实很适合作为辅助人类的工具。但当业务链路中出现大规模数据处理的需求时，这种模式就捉襟见肘了。目前很少有产品能原生提供上传一批数据、配好处理规则、再稳定地逐条跑完的能力。DataPilot 就在一个开源 Agent 平台基础上做了大量改造，补齐了这块“批量执行”的拼图。

### 批量处理的核心门槛在于状态追踪与容错

处理一万条数据，如果只是简单写个 for 循环逐条执行，系统将完全不具备容错能力。跑到第三千条时哪怕出现一次网络闪断，前面的进度都会全部作废；如果跑批结束后发现有几百条处理失败，开发者也很难从海量结果中把它们单独捞出来重试；更致命的是，如果输出的数据格式不规范，往往要等到业务方实际使用时才会被发现。

为了解决规模化带来的痛点，DataPilot 的批量执行引入了细粒度的状态追踪机制：中断了能从断点继续，已完成的不重复跑，失败的自动重试，格式不对的自动打回重跑。同时，考虑到搜索、爬取这类外部服务在并发调用下极易熔断，我们在系统里配置了多个供应商做动态兜底。最终处理完的整批结果，可以直接生成独立页面交付给业务方。

## 从凭感觉调参到建立自动化评测机制

批量执行能力有了之后，我开始大规模跑业务数据。质量问题很快暴露出来。

实际的业务数据往往是非常“脏”的：简历里可能只写了公司名没写职位，公司名可能是半中半英还带各种奇怪符号，爬下来的调研文本可能跟话题完全无关。这些在跑 Demo 时根本碰不到的坑，在真实的业务数据里却到处都是。

多数人的做法是凭感觉调 prompt。改了一版觉得好像好了一点，改了第二版觉得某些地方退步了但说不清楚，到第三版已经记不住第一版什么样了。没有度量手段，就只能靠印象判断质量。

Better Skills 的解法是给每个 skill 挂载一套真实的回归测试集。跑完之后，引入一个独立的 AI 来当“判卷人”。被测的 skill 和判卷的 AI 在物理上是隔离开的，坚决杜绝“自己给自己打分”的糊涂账。为了验证某个 skill 到底有没有用，我还会对同一个 case 跑 A/B 测试（用了 skill VS 没用 skill）。有了这套机制，每次改动的效果都清清楚楚地记录在案。

以前改一版只能说"好像好了一点"，现在能看到通过率从 65% 涨到 82%，同时看到两个边界 case 退步了，能定位到是哪条规则改动导致的。

### 测试集不是“脑暴”出来的，是从报错日志里捞出来的

真实的生产业务远比理想状态复杂：用户会问不合理的问题，输入的数据会残缺，格式也会错乱。如果测试用例只覆盖正常场景，就无法验证 Agent 的鲁棒性。因此，高质量的测试集绝不是工程师憋在屋子里“脑暴”出来的，而是直接从线上跑挂的报错日志里捞出来的。把每次出 Bug 的现场“脏数据”、异常输入和边界 Case 沉淀成固定的回归用例，才能真正还原生产环境的恶劣。

### 预期结果：从“标准答案”转向“验收标准”

每个 case 配一个预期结果，说明这条输入应该产出什么。但预期不是精确到字符的标准答案，因为很多任务的合理输出不止一种。这里的预期更像是“验收标准（Rubric）”，而不是用来做简单的字符串对比。

由于输出是开放式的，硬编码的字面对比肯定行不通。这也就是为什么我们需要前文提到的那个“独立的 AI 判卷人”：由它来根据验收标准，判定大模型的输出是否真正达标。只要实际结果在语义和逻辑上符合要求，哪怕字面说法不同，也会被准确判定为通过。

### 评测维度：不仅看最终输出，更要断言（Assert）执行过程

自动化评测跑完后，通常会暴露出一批 bad case。有些是 Prompt 缺陷，有些则是“预期标准”本身不合理需要修正。

但最危险的是那些错得非常“隐蔽”的 case。比如：Agent 在执行时本该去搜索某个企业信息，但碰巧搜索服务挂了。合理的做法是报错并停下来，但 Agent 却根据模型记忆硬编了一个答案，格式完美，内容碰巧也是对的。如果只对比最终结果，这条测试绿了。但这其实是一次彻头彻尾的“侥幸过关”。在海量数据跑批时，一个靠运气蒙对的结果，往往比明确的报错更可怕，因为它会悄无声息地掩盖掉底层服务的致命漏洞。

这次踩坑让我在评测机制中加上了一道硬卡点：必须在自动化脚本中严格断言（Assert）执行过程。我们会提取 Agent 运行时的 `tool_calls` 记录，如果它在这道题里根本没有发起 `search` 请求，哪怕最终答案对了，也会被直接打回并标记为 Fail。

## 操作边界：用 CLI 划定 Agent 的行动边界

Talent Graph 做的是人才标签。业务方需要大量自定义标签：985 院校、大厂经历、管理经验、量化背景。处理这些非标数据需要组合各种复杂的 Agent 能力。但当 Agent 拥有的能力越来越多，如何防止它乱来？

这就涉及到了 Harness 工程中极其重要的一环：为 Agent 提供什么样的工作环境。

### CLI 是收敛不确定性的天然容器

我们最终选择 CLI（命令行）作为 Agent 操作这套标签系统的唯一接口。从外围约束（Harness）的视角来看，CLI 不仅仅是为了“通用”，更是为了“收敛”。

自然语言是模糊且极易发散的，但 CLI 命令是极其严谨和确定的。Agent 想要执行任何操作，都必须将模糊的意图翻译成严格遵循语法的 shell 命令。CLI 就像是一个天然的“沙盒”与“漏斗”：
1. **统一的观测与拦截：** Agent 敲下的每一行命令都可以被日志系统精准记录，这为后续的审计和回溯提供了极其清晰的 Execution Trace。
2. **极低的试错成本：** 当 Agent 传错参数或违背逻辑时，CLI 会返回标准化的退出码（Exit Code）和 `stderr` 报错流，这种结构化的错误信息极其适合 Agent 读取并自我修正。

通过限制 Agent 只能在 CLI 环境中“敲代码”，我们实际上把它不可控的“自由意志”，强制收束在了系统预先定义好的操作边界内。在[面向 Agent 的 CLI 工具设计](/blog/cli-design-for-ai-agents)中，我曾详细展开过这种设计带来的系统稳定性红利。

## 规则工程化：用工具的“硬校验”替代 Prompt 的“软约束”

在复杂的业务逻辑下，怎么确保 Agent 不折不扣地按规则操作？

在早期的 [Dossier](/projects/dossier) 项目里我吃过亏。当时有一条规则：“写入研究记录时必须附带可信度评分”。我把这句话用大写加粗写在 prompt 里，结果 Agent 还是动不动就忘。后来我想通了，把它改成了工具的必填参数，不传就直接报错（抛 Exception），并且在报错信息里把打分标准塞进去。改完之后 Agent 再也没忘过，因为不传参数它根本走不下去。

Talent Graph 里有两类规则需要管理。一类是操作约束，能编进工具的全部编进去。另一类是领域判定标准，什么学校算 985、哪些公司算大厂，这些需要文本描述，编不进工具参数，但组织方式同样需要设计。

### 权限隔离：对 Agent 彻底隐藏非必要命令

默认只开放查询，写入操作需要显式开启。一个只开放了查询权限的 Agent，连写入命令的存在都看不到，从根本上杜绝了误操作。

### 逻辑防呆：把业务校验前置到工具内部

除了权限隔离，业务逻辑的防呆机制也应该交给工具。比如在创建新实体时，工具内部会自动检查是否已存在相似实体，一旦发现就直接报错并提醒复用。这些复杂的逻辑校验根本不需要在 Prompt 里反复跟 Agent 强调，工具的代码直接就替它兜底了。写入操作统一收拢到工具层后，系统还能顺手记录完整的审计日志，一旦出问题可以精准追溯。

### 错误处理：用详尽的报错引导 Agent 自我修复

Agent 执行过程中碰到错误是常态。如果报错只说"参数错误"或"操作失败"，Agent 大概率会卡住或者乱猜着重试。相反，如果提供具体的修复建议，比如：“未找到公司信息，请先调用 `search_company` 工具获取 `company_id` 后，再执行写入命令”，Agent 看到提示就能自己修正流程继续跑。这样就不需要人介入。

### 规则治理：按任务动态加载，避免 Attention 失焦

如果把几十上百种标签的判定规则全塞进系统提示词里，不仅极易引发规则冲突，更致命的是会导致大模型 Attention 机制的失焦（Lost in the middle）——它会开始随机忽略部分上下文并产生幻觉。

因此，我将复杂的判定标准按任务进行了拆分解耦。当 Agent 执行“985 院校”判定时，只向其注入院校相关的标准文档。按需动态注入本质上是为了缩小 Agent 的动作空间，让它只专注眼前任务的约束。这也让规则的维护变得像管理代码片段一样清晰：新增标签只需新建一份文档，修改规则也不会误伤其他逻辑。

## 结语：在 Prompt 之外，建立工程护栏

在做 Agent 业务的初期，我们很容易对大模型的“聪明程度”产生路径依赖，将大部分精力投入到 Prompt 的调优上。

但经过这一年的落地打磨，我的体会是：Prompt 决定了 Agent 能力的上限，但纯粹的 AI 能力在复杂的业务链路中往往显得脆弱且不可控。工业级 Agent 的可靠性，绝不能仅仅依赖模型本身的聪明才智自然“涌现”。

Agent 的规模化落地，最终不可避免地需要回归到经典的软件工程。我们需要在 Prompt 之外，踏踏实实地去构建外围的基础设施：完善失败重试逻辑、补充自动化断言脚本、将易错的业务规则封装成强校验的工具。只有用这些枯燥但确定的代码去死死兜住大模型的下限，它才能真正走出脆弱的对话框，稳稳地运转在核心业务的生产线上。
