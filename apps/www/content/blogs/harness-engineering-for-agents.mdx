讨论 Agent 如何落地时，大家往往更关注模型能力和 Prompt。它们确实会影响 Agent 的表现，但还不足以让一套系统在生产环境里稳定运行。

过去一年，我一直在实际业务中做 Agent 项目。很多时候，功能已经跑通，离稳定交付仍然很远。中间还有大量具体工作，最后都要靠工程系统来完成。

行业里通常把这部分工作称为 Harness Engineering。它讨论的是 Agent 运行所依赖的工程系统如何设计。本文结合一些实际项目，记录我在这方面的做法和思考。

## 从单次对话到生产级批量处理

我们遇到的很多需求，都需要 Agent 按照同一套标准处理一批数据。公司名称标准化就是一个典型例子。“字节”“ByteDance”“字节跳动（上海）有限公司”写法不同，在数据库里却应该指向同一家公司。几千份简历的结构化提取也有类似的要求：每份简历的内容不同，最后交付的字段和格式必须一致。

现有的通用 Agent 产品，大多以一次对话为基本单位。用户交给 Agent 一项任务，拿到结果，这次处理也就结束了。把同样的方式扩展到几千条数据，还需要一套系统来组织和管理整批任务。DataPilot 在一个开源 Agent 平台上增加了批量执行能力，处理的就是这部分工作。

![DataPilot 的批量处理界面](/projects/datapilot/batch-processing.png)

### 状态追踪和失败恢复

简单写一个 for 循环，当然也能逐条处理一万条数据。问题是任务未必能一次跑完。假设处理到第三千条时网络中断，系统需要知道前面哪些已经完成，当前这一条是否成功，重新启动后又该从哪里继续。如果没有提前记录这些状态，恢复任务就会变成一次人工对账。

DataPilot 会记录每条数据的处理状态。进程重启后，它可以从未完成的地方继续，不会把已经成功的部分再跑一遍。失败项会保留在任务里，修好问题后可以单独重试。输出还会经过格式校验，避免整批处理结束后才发现结果无法使用。

批量任务也会放大外部服务的不稳定。搜索或爬取服务偶尔失败，在单次使用时可能不明显；并发处理大量数据时，这类错误会频繁出现。为此，系统配置了多个服务商，其中一个不可用时可以切换到其他服务继续执行。

## 从凭感觉调参到建立自动化评测机制

批量任务跑起来后，真实业务数据里的各种问题很快会集中冒出来。一份简历可能只写了公司名，没有职位。同一家公司的名字也可能混着中英文、括号、空格和各种特殊符号。爬取回来的调研材料，有时只是碰巧命中了关键词，内容跟原来的问题毫不相关。数据只有几条时，人工看一眼还能发现；一次跑上千条，漏掉的问题就会直接混进结果里。

调 Prompt 很容易越调越没底。刚发现的 bad case 修好了，看起来这一版是好了一点；可旧 case 没有一起重跑，谁也不知道是不是又改坏了别的地方。

我用 [Better Skills](/projects/better-skills) 给 Skill 做自动化评测，把这些 bad case 组成固定的回归测试。以后再改 Skill，之前遇到过的问题都会跟着重跑，不用再靠记忆判断这一版到底好不好。

![Better Skills 评测面板](/projects/better-skills/dashboard-portfolio.png)

### 从报错日志中补充测试用例

真实业务里的输入经常不完整，格式也不统一，用户的问题有时也不合理。测试集如果只放正常 case，就看不出 Agent 遇到这些情况时会怎么处理。

很多问题只有任务真正跑起来以后才会暴露。Better Skills 的测试集会继续收录实际任务中出现的问题。报错日志里有原始输入和执行记录，问题复现后，我会补上验收标准，作为后续的回归用例。

### 为每个 case 写清楚验收标准

测试用例确定以后，还要说明什么样的结果算通过。Agent 的输出通常没有唯一答案，同一个要求可以有多种正确写法。逐字比较会把一些合理的结果也判成错误。

Better Skills 会为每个 case 写下一组具体的验收条件。以企业标签为例，可以分别检查应该关联的公司是否完整、有没有加入不属于这个标签的公司，以及输出文件的格式是否正确。

评分时，Better Skills 使用 LLM-as-a-Judge，让另一个独立的 LLM 阅读 Agent 的实际输出，按照这些条件逐条判断。每条判断的依据都会保留下来，后续可以人工复核。

### 评测也要检查执行过程

上一节的验收标准主要检查最终结果。实际评测时，还要看 Agent 是怎么得到这个结果的。

我遇到过一个 case：Agent 原本需要搜索某家企业的信息，执行时搜索服务刚好失败。它没有拿到搜索结果，还是根据模型记忆给出了答案。这次答案碰巧是对的，格式也符合要求。如果只检查最终输出，这条 case 会正常通过。

Better Skills 会把执行过程也纳入验收条件。以这个 case 为例，评测会先确认 Agent 有没有调用搜索。没有拿到可靠结果时，Agent 应该停下来并说明原因。这样做虽然没有完成任务，处理方式仍然是正确的；继续用模型记忆写入答案会被判为失败，哪怕最后碰巧答对。

## 用 CLI 限制 Agent 的操作范围

我在 [Talent Graph](/projects/talent-graph) 里用 Agent 维护人才标签。业务方可以定义 985 院校、大厂经历、管理经验、量化背景等标签，Agent 负责搜索相关企业和院校、创建实体、补充别名并维护标签关系。这些操作涉及业务数据写入，操作范围需要由系统明确控制。

我把 CLI 作为 Agent 操作 Talent Graph 的唯一入口。每个命令能做什么、需要哪些参数，都由工具预先定义。Agent 对任务的理解可以来自自然语言，真正执行时仍要落到有限的命令和参数上。

![tableau-cli 的命令行帮助信息](/projects/tableau-cli/tableau-cli-help.png)

CLI 的每次调用都可以记录下来。参数错误或操作失败时，工具会返回明确的原因，Agent 可以据此调整下一步，出了问题也能回看它执行过哪些命令。关于 CLI 面向 Agent 的具体设计，我在[面向 Agent 的 CLI 工具设计](/blog/cli-design-for-ai-agents)里单独写过。

## 把操作规则写进工具

我在 [Dossier](/projects/dossier) 里用 Agent 整理调研资料。不同来源的证据强弱不一样，所以每条研究记录都要附带可信度评分。

我把这条要求写进 Prompt，还特意用了大写和加粗，Agent 依然会漏掉。评分改成写入工具的必填参数后，没有评分的记录无法写入；工具同时会返回评分标准，Agent 补上以后才能继续。

这件事也影响了我在 Talent Graph 里处理规则的方式。权限、必填字段和重复实体由工具直接检查。哪些学校算 985、哪些公司算大厂，会写在独立的规则文档里，由 Agent 在相关任务中读取。

### 只开放当前任务需要的命令

Talent Graph 默认只开放查询。需要修改数据时，系统才会为当前任务开启相应的写入命令。一个只负责查询的 Agent 看不到这些命令，也不会在执行中误调用它们。

### 业务校验由工具完成

创建新实体前，工具会检查数据库中是否已经存在相似实体。发现重复时，写入会被拒绝，并提示 Agent 复用已有实体。这条规则不需要在 Prompt 里反复强调，每次写入都会经过同样的检查。

所有写入操作也会留下审计记录。出了问题，可以回看 Agent 当时调用了什么命令、修改了哪些数据。

### 报错时说明下一步怎么做

“参数错误”或“操作失败”只说明这次调用没有成功，Agent 并不知道接下来该改什么。工具需要把原因和可行的处理方式一起返回。

例如，写入记录时缺少 `company_id`，错误信息会提示 Agent 先调用 `search_company` 查找公司，再使用返回的 `company_id` 继续写入。Agent 可以根据这条提示修正调用，不需要等待人工处理。

### 规则文档的渐进式加载

领域判定标准仍然要以文本形式提供给 Agent。Talent Graph 把通用方法留在 Skill 中，具体领域规则拆成独立文档。Agent 先判断当前任务，再读取对应的规则文件。处理“985 院校”时，加载院校标准；处理企业标签时，加载企业分类规则。

这是一种渐进式加载。上下文先获得完成任务所需的通用方法，具体规则在任务明确后才进入。几十种标签不必同时占用上下文，每类规则也可以单独维护。

## 结语

Harness Engineering 用到的很多方法并不陌生。Agent 进入真实业务以后，模型带来的不确定性，还是要靠这些熟悉的工程方法处理。
