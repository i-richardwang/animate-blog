talent-graph 项目里有一个标签清洗的场景。给定一个标签名称，让 Agent 搜索确认这个标签包含哪些实体，在知识图谱中创建对应的实体并关联上去。

边界情况比预想的多。MBB 只有 McKinsey、BCG、Bain 三家，Deloitte 和 Accenture 看起来也像，但不属于 MBB。藤校是 Ivy League 的 8 所，MIT 和 Stanford 不是。母子公司归属也有讲究。菜鸟属于阿里巴巴集团，"物流公司"标签应该直接挂菜鸟，而"互联网公司"标签挂阿里巴巴时，菜鸟通过层级关系自动继承。

这些情况的共同点是，人凭常识觉得答案很明确，但 Agent 的判断路径不一样。它可能优先依赖训练数据里的模糊关联，而不是先去搜索确认。每次改一版 Skill 就得把这些测试全部重跑一遍。手动跑效率低，而且容易遗漏。之前已经通过的测试是不是退步了，看不出来。

Better Skills 就是为了解决这个问题做的评测工具（功能和技术架构见[项目页](/projects/better-skills)）。

实际跑下来发现，评测没那么简单，它是层层嵌套的。测试用例选不对，后面的验证条件设计就白费。验证条件没拆好，基线对比不可靠。基线没有真正隔离，差异来自哪里说不清楚。评分不可信，前面所有工作白做。

## 测试用例要有区分度

早期选的测试用例太简单。比如让 Agent 给"MBB"创建标签。三家公司是常识，模型本身就知道答案。有 Skill 和没 Skill 的通过率完全一样，评测跑了等于没跑。

后来换了更难的测试用例才看出差异。比如某个地域性的行业分类，涉及的公司列表不是常识，必须搜索才能得到正确答案。在这类测试用例上，有 Skill 的 Agent 知道先搜索后写入，没有 Skill 的更依赖自己的知识作答。两者的通过率拉开十几个百分点。

简单测试用例上 Skill 的贡献往往体现在效率上，token 消耗减少 80% 以上，但正确性方面差别不大。正确性的差异需要足够难的边界情况才能暴露，而且这个测试用例必须命中 Skill 真正介入的那个决策点。如果测试用例选的不是这个点，验证条件写得再精细也测不出有意义的信号。

## 验证条件要拆细

每个测试用例只给一个通过或不通过是不够的。以 MBB 为例，我们拆成了五条验证条件：

1. 创建了标签，基本字段完整
2. 关联了 McKinsey & Company、Boston Consulting Group、Bain & Company
3. 没有误挂 Deloitte、Accenture、Strategy& 等非 MBB 公司
4. 写入前用了搜索工具核实
5. 输出文件格式符合要求

一个测试用例的通过率可能是 4/5。如果某轮改动让第 3 条从通过变成失败，可以精确定位是"不误挂"这个能力退步了。

拆细之后才发现，有些验证条件在测结果，有些在测过程，两者意义完全不同。

搜索工具因为外部原因挂了。一个 Agent 没搜到结果，根据自己知识编了个答案，恰好蒙对了，MBB 确实是那三家。结果验证条件全部判定为通过。但这个测试用例应该判失败，因为下次遇到不是常识的标签，同样的行为会导致错误的结果。另一个 Agent 同样遇到搜索故障，选择了中止任务，不写入任何结果。标签清洗没完成。但工具不可用时停下来而不是瞎猜，这个测试用例应该判通过。

结果验证条件只能检查最终产出对不对，过程验证条件才能检验 Agent 的决策方式对不对。两个维度必须同时覆盖。实践中形成了一套习惯，先列结果相关的，比如写入了什么、没写入什么，再补过程相关的，比如是否搜索、是否验证、工具不可用时的行为，最后加格式相关的。过程验证条件容易被忽略，但区分"碰巧对了"和"可靠地对"靠的就是它。

## 基线隔离没这么简单

评测的核心设计之一是双配置对比。每个测试用例同时在加载 Skill 的配置和不加载 Skill 的配置下跑。但"不加载 Skill"比听起来难实现。

早期不加载 Skill 的做法是不把 SKILL.md 注入 system prompt，但 prompt 里仍然提到了 skill 名称和项目路径。用 Claude Sonnet 做执行 Agent 时，它遵守了约束，没有去读 SKILL.md。换成另一个模型后，Agent 直接搜索到了 `.claude/skills/` 目录下的 SKILL.md 并读取了内容，完全无视 prompt 中的限制。两个模型在不加载 Skill 配置下的行为完全不同。一个真的没有 Skill 指导，另一个自己把 Skill 找出来读了一遍。加载 Skill 和不加载 Skill 的差异失去了意义。

后来改成把每次运行放到 `/tmp` 下的独立目录执行，输入文件只保留文件名暂存进去，项目里的 `.claude/skills/`、`CLAUDE.md` 等配置对执行 Agent 完全不可见。不管模型有多主动，它物理上接触不到 Skill 文件。

还踩过另一个坑。某轮迭代同时修改了 Skill 内容和切换了执行 Agent 的模型。通过的比例出现变化，但说不清楚是 Skill 改动还是模型差异导致的。后来在迭代记录里加了执行 Agent 和评分 Agent 的模型标识，回溯时至少能识别出哪些迭代涉及了模型切换。

## 评分 Agent 会假阳性

评分 Agent（Grader）是另一个 Agent，它审查执行 Agent 的完整执行记录和输出文件，逐条给出判定。评分 Agent 的工作质量直接影响评测的可信度。

早期遇到过加载 Skill 和不加载 Skill 的通过比例都是 100% 的情况，但不加载 Skill 消耗的 token 只有 186，加载 Skill 的有 1590。不加载 Skill 用不到 200 tokens 就"完成"了任务并且全部判定为通过。这是评分 Agent 在假阳性。问题出在验证条件措辞太宽泛。"Agent 创建了标签并关联了正确的实体"，评分 Agent 看到执行记录里有 `tag add` 的调用就判定为通过，没有验证参数是否正确、实体是否完整。

解决方向是让验证条件更具体。"关联了正确的实体"拆成三条独立验证条件，每条指定具体的公司名称，每条都需要评分 Agent 在执行记录中找到证据。"没有误挂"也拆成显式的负面检查。粒度越细，评分 Agent 假阳性的空间越小。如果不加载 Skill 的 token 消耗和加载 Skill 的差距很大但通过比例完全一样，大概率是评分 Agent 区分力不够。

## 验证条件本身也可能写错

评分 Agent 的问题相对容易发现。还有一类问题更隐蔽，验证条件自身就有 bug，而且可能长期不暴露。

遇到过一条验证条件要求实体的标准名称用中文，"麦肯锡"而不是"McKinsey & Company"。用 Claude Sonnet 做执行 Agent 时一直通过，Sonnet 习惯于用中文。换成 GLM 后就失败了，GLM 倾向于用英文官方名。排查后发现 SKILL.md 里的措辞是"取业内最通用的指代方式"，并没有要求必须用中文。两个模型的选择都在允许范围内。问题出在验证条件自行创造了 Skill 没承诺的标准。

这类 bug 只要执行 Agent 模型不变就永远不会暴露。只有在模型切换或 Skill 内容变化时，之前一直通过的验证条件突然失败，才会倒查出来。修复分两步，删掉这条验证条件，同时在 SKILL.md 中补充更明确的说明，两个层面各自收敛。

还有一种情况也遇到过。有些验证条件在检查 Agent 的总结输出，prompt 要求 Agent 最后写几行总结，验证条件跟着解析总结里的字段。但业务正确性从 Agent 调用的 CLI 命令就能读出来，总结行只是给人看的。Agent 可能做对了所有操作但总结格式不对，也可能操作全错但总结看起来很漂亮。后来删掉了 prompt 中的强制总结段，改为从执行记录中的工具调用序列判定业务结果。

评测体系里的每个环节都会影响最终结果的可信度。测试用例要命中 Skill 的决策点，验证条件要拆得够细而且要分开测过程和结果，基线要真实隔离，评分 Agent 要能准确判定。任何一个环节出问题，评测数据就不值得信任。

围绕 Agent Skill 的工程工作不止评测这一块，还包括工具接口设计，比如 CLI 的错误信息应该告诉 Agent 下一步做什么，上下文管理，比如 Skill 按需加载而不是一次性灌进去，运行时兜底，比如搜索服务挂了有备用 provider。这些工作合在一起，构成了围绕 Agent 的一整套支撑体系。评测是其中的验证层。验证层不可靠，其他层的改进也就无从判断。
